# Qdrant 1.17 → 1.18 Bump — Design (Foundation)

**Date:** 2026-06-29 **Status:** approved **Epic:** `tea-rags-mcp-62zf` (Migrate
to Qdrant 1.18) **Type:** `chore` / `config` — version-bump mechanics only

This is the **foundation** design of the Qdrant 1.18 migration. Two dependent
designs build on top of it and are specified separately:

- `2026-06-29-qdrant-turbo-quant-design.md` — TurboQuant (feat, default ON)
- `2026-06-29-qdrant-1.18-capabilities-design.md` — remaining 1.18 server
  capabilities (memory guard, reindex perf, memory reporting, low-mem mode)

Both require this bump to land first (TurboQuant + strict-mode config + the
`/memory` endpoint do not exist before 1.18).

---

## 1. Decision of record

| Item                                         | Value                          |
| -------------------------------------------- | ------------------------------ |
| Embedded daemon **server** version           | **1.18.2** (latest 1.18 patch) |
| External Qdrant **minimum** accepted version | **1.18.2** (same constant)     |
| `@qdrant/js-client-rest` **SDK**             | **1.18.0** (latest published)  |

`.qdrant-required-version` is the **single source of truth** (rule
`.claude/rules/qdrant-required-version.md`). It plays two roles at once — the
version the embedded daemon downloads, and the minimum accepted external server
version. We deliberately pin the **latest patch 1.18.2** rather than 1.18.0:

- **Gain:** embedded daemon gets every 1.18.x fix immediately (filtered-search
  perf, TurboQuant heap-reporting fix, snapshot-transfer timeout, security
  patches).
- **Accepted cost:** external-min is also 1.18.2, so a user running an external
  Qdrant at 1.18.0/1.18.1 will be rejected with `QdrantVersionTooOldError`. This
  is a knowingly strict floor — the alternative (splitting the constant into
  `embeddedVersion` vs `minExternalVersion`) is an architecture change to
  `qdrant-version.ts` and is **out of scope** for a version bump.

The cosmetic number mismatch (1.18.2 server / 1.18.0 SDK) is benign — they are
two independent artifacts. The SDK 1.16→1.17 step was already completed (beads
`doe6`, closed); this design advances both to 1.18.

## 2. Changes by area — _what it gives / what changes_

### A. Config / deps — 3 files

**What it gives:** the whole bump is driven by one constant + one dependency.
The embedded download URL is auto-derived from the constant
(`releases/download/v${QDRANT_VERSION}/${asset}` in
`src/core/adapters/qdrant/embedded/download.ts:54`), and the external-version
guard reads the same constant.

**What changes:**

1. `.qdrant-required-version`: `1.17.0` → `1.18.2`.
2. `package.json`: `"@qdrant/js-client-rest": "1.17.0"` → `"1.18.0"` (exact pin,
   no caret — matches current convention).
3. `package-lock.json`: regenerate via `npm install` (updates `version`,
   `resolved`, `integrity` for the SDK and any transitive deps).

### B. Source code — ZERO changes

**What it gives:** confirmation that no runtime code is touched, so the
architectural-hub `errors.ts` (fanIn 12, transitiveImpact 39) is **not** a blast
radius — only the _value_ of `QDRANT_VERSION` and the error **message strings**
flow through it, never the signatures.

**What changes:** nothing in `download.ts`, `daemon.ts`, `qdrant-version.ts`,
`errors.ts` — they all read `QDRANT_VERSION` or receive versions as arguments.

### C. Tests — 1 mandatory file + 1 correctness fix

**What it gives:** keeps the suite green and removes a brittle hard-coded
fixture so future bumps don't touch these tests.

**What changes:**

1. `tests/bootstrap/qdrant-compat-check.test.ts` — 4 hard-coded `1.17.0`
   literals (lines 32, 55, 80, 88) currently equal the min-required version and
   will break after the bump (mocks become "below minimum", so the "passes when
   equals" cases start throwing). Replace the literals with a dynamic import of
   `QDRANT_VERSION` (pattern already used in `version-lock.test.ts:55`), **not**
   with a `1.18.2` literal:
   - L32 `version: "1.17.0"` → `version: QDRANT_VERSION`
   - L55 `stringContaining("1.17.0")` → `stringContaining(QDRANT_VERSION)`
   - L80 `"v1.17.0"` → `` `v${QDRANT_VERSION}` ``
   - L88 `version: "1.17.0"` → `version: QDRANT_VERSION`

   This is **not** a business-logic rewrite — the asserted behaviour ("passes
   when server == required") is preserved; only the fragile fixture is removed.

2. _(correctness)_ `tests/core/adapters/qdrant/embedded/version-lock.test.ts:51`
   — `not.toBe("1.17.0")` → `not.toBe(QDRANT_VERSION)`. After the bump the
   current literal passes trivially (`0.0.1 ≠ "1.17.0"`) for the wrong reason;
   binding it to `QDRANT_VERSION` makes the assertion honest.

**Tests deliberately NOT touched** (remain valid against the 1.18.2 floor):

- `downgrade-guard.test.ts` — `1.10.0` is still `< pin`, `2.5.0` is still
  `> pin`; the `1.17.0\n` parse sample is an arbitrary trim fixture, not a pin
  reference.
- `qdrant-version.test.ts` — `compareSemver`/`isSemver` use `1.17.0` as generic
  semver samples, unrelated to the pin; the file-equality test reads the version
  file dynamically.
- `download.test.ts` — reads `QDRANT_VERSION` dynamically.

### D. Docs / release

**What it gives:** a discoverable, BREAKING-flagged record for external-Qdrant
users.

**What changes:**

1. `CHANGELOG.md` — entry + **BREAKING** note: external Qdrant `< 1.18.2` now
   fails startup with `QdrantVersionTooOldError`.
2. Commit: single `feat(config)!: bump Qdrant server to 1.18.2 + SDK 1.18.0`
   with a `BREAKING CHANGE:` footer (per `.claude/rules/commit-rules.md`).
   `website/docs/changelog.md` is auto-generated by semantic-release — not
   hand-edited.

### E. Live validation gate — RocksDB forward-compat

**What it gives:** the only real risk of the bump. Qdrant 1.18 fully removed
RocksDB; the embedded daemon's on-disk storage (written by 1.17) must migrate
forward when the 1.18.2 binary cold-spawns on it. `assertNoDowngrade`
(`download.ts:76`) already blocks the reverse direction.

**What changes:** no file edit — a **user-triggered** validation step:

1. Cold-spawn the 1.18.2 daemon on an existing 1.17 storage and verify the index
   reads back cleanly. Run via the `test-self-reindex` skill against a
   `tea-rags-worktree` alias (build + `npm link` + reindex the worktree, **not**
   `main`), so the shared `main` index is untouched. This is the gate before
   merge — green tests are necessary but not sufficient here.

### Full 1.18.0 surface (exhaustive — for "is this really everything?")

1.18.0 ships **5 Features + 20 Improvements**. The first-party changelog
explicitly confirms there are **no** new query/search capabilities in 1.18 — no
faceting, distance matrix, score boosting / formula queries, MMR, RRF changes,
ACORN filters, server-side inference, multi-vector/ColBERT, new payload index
types, or partial vector updates. 1.18 is a **quantization + memory +
storage-cleanup** release, which is why the applicable-feature list is short by
nature.

**5 Features** → TurboQuant (turbo design), named-vectors API (beads `bx9m4`,
excluded), deep memory reporting (capabilities 3c), low-memory mode
(capabilities 3d), strict-mode reject-on-high-memory (capabilities 3a).

**Transparent improvements (arrive free with the bump — NO code):**

- Dynamic CPU pool for search workers (better perf under IO wait)
- Fully remove RocksDB (storage simplification — see forward-compat gate E)
- Deterministic HNSW sub-graph building + deterministic structure ordering
- **Cosine normalization SIMD on ARM CPUs** (free perf on this Darwin arm64
  host)
- Reduce immutable geo-index memory by 7x (n/a unless geo payload indexed)
- Don't hold shard-holder lock during search (less blocking)
- Don't stall update queue waiting for deferred points
- 60s default timeout on update requests + long-running cleanup
- Clear optimizer errors on optimizer recreation
- Clean temp directories before loading collections
- Snapshot-based shard transfers (faster recovery) + receiver pre-clear
- Operation-size-based batching in shard transfers
- Patch-line transparency (1.18.1/1.18.2): io_uring quantized multi-vector
  scorers, filtered-search + integer-range + `match:{except:[]}` fixes,
  payload-index `on_disk` flip without rebuild, snapshot-stream timeout,
  security fixes (REST auth whitelist bypass, malicious-snapshot heap read)

Listed only so the bump's full surface is visible; nothing in tea-rags changes
to consume them.

### Explicitly skipped 1.18 features (not applicable to embedded single-user)

- Audit-log additions (API method path, tracing ID, audit config in
  telemetry/metrics, skip-audit-on-telemetry) — no audit subsystem in embedded
  single-user mode.
- Request Tracing IDs (`traceparent`), Per-Collection `/metrics`, internal gRPC
  auth, snapshot-restore-from-URL toggle.
- "Link to agentic skills in startup message" — cosmetic daemon log line.

### F. Environment-variable docs + release-notes env-reporting (cross-cutting)

The bump itself adds no env var, but the dependent designs (turbo, capabilities)
do. Two policies apply to **every** new/changed env across all three designs and
become the **standing convention** for all future env changes — defined here in
the foundation so the other specs can reference it.

**F1 — Documentation (single source).** Every new or changed env var is recorded
in `website/docs/config/environment-variables.md` (central table, format
`| Variable | Description | Default |`) **and** `.env.example`. Qdrant-specific
vars also go in `website/docs/config/qdrant.md`. The migration's full env set:

| Variable                             | Description                                         | Default     | Design          |
| ------------------------------------ | --------------------------------------------------- | ----------- | --------------- |
| `QDRANT_TURBO_QUANT`                 | Enable TurboQuant 8x dense-vector quantization      | `true`      | turbo           |
| `QDRANT_MAX_RESIDENT_MEMORY_PERCENT` | Reject writes above N% system RAM (1–100)           | unset (off) | capabilities 3a |
| `QDRANT_LOW_MEMORY`                  | Force on-disk storage to minimize RAM               | `false`     | capabilities 3d |
| `QDRANT_SEARCH_MAX_BATCHSIZE`        | Cap batch-search size (only if confirmed in 1.18.0) | unset       | capabilities 3e |

**F2 — Release notes always surface env changes.** Extend the release pipeline
so any release that introduces or changes env vars renders a dedicated
**Environment Variables** section, each entry formatted
`ENV_NAME · what it does · default` with a new/changed marker. Touch points:

1. `scripts/release-changelog-prompt.md` — add a rule + a new `envChanges[]`
   field to the `release-notes.json` schema. The agent extracts env
   additions/changes from commit subjects/bodies (`BREAKING CHANGE` footers +
   `config`/`bootstrap`-scope commits) into
   `{ name, description, default, change: "new" | "changed" }`.
2. The changelog renderer that consumes `release-notes.json`
   (`scripts/build-changelog-artifacts.js`) — render `envChanges[]` as its own
   section in both the changelog and the GitHub release body.

Scope: `scripts` / `website` (non-release). Ships with the migration but is a
standing convention for ALL future env changes, not only Qdrant's.
