# Qdrant 1.18 Remaining Server Capabilities — Design

**Date:** 2026-06-29 **Status:** approved **Epic:** `tea-rags-mcp-62zf` (Migrate
to Qdrant 1.18) **Type:** `feat` **Depends on:**
`2026-06-29-qdrant-1.18-bump-design.md` **Absorbs beads:** `tea-rags-mcp-b1rs`
(Auto-tune `max_resident_memory_percent`)

The remaining applicable 1.18 server capabilities, grouped into one spec (their
common thread: Qdrant `strict_mode_config` / memory / optimizer config). Each
sub-feature is independent and can be implemented and shipped on its own; they
share one mechanism — startup reconcile of per-collection config — already
introduced by the TurboQuant design.

Out of this spec: TurboQuant (own design), Named Vectors (beads `bx9m4`),
transparent 1.18 improvements (arrive with the bump), and embedded-irrelevant
features (audit logs, tracing, per-collection `/metrics`, gRPC auth).

---

## Shared mechanism — per-collection config reconcile

`max_resident_memory_percent` and `search_max_batchsize` live in the
**per-collection `strict_mode_config`** (set via `create_collection` /
`update_collection`). The TurboQuant design already adds a startup reconcile
(`factory.ts#resolveInfrastructure`: `getCollectionInfo` → diff → update). This
spec **extends the same reconcile** to also converge `strict_mode_config`, so
existing collections pick up the guards without a reindex. One idempotent
reconcile pass converges quantization **and** strict-mode config together.

---

## 3a. `max_resident_memory_percent` — OOM guard

**What it gives:** the embedded daemon rejects memory-consuming write operations
(`upsert`, `set payload`) when process resident memory exceeds N% of total
system memory (valid range 1–100). Turns the 30 GB OOM crash class (epic `gmuf`)
into a managed, typed rejection instead of a daemon kill mid-ingest.

**What changes:**

1. `src/core/contracts/types/config.ts` — `QdrantTuneConfig` gains
   `maxResidentMemoryPercent?: number`.
2. `src/bootstrap/config/schemas.ts` + `parse.ts` — env
   `QDRANT_MAX_RESIDENT_MEMORY_PERCENT` (number, validated 1–100; unset = guard
   off).
3. `src/core/adapters/qdrant/client.ts` `createCollection` — when set, emit
   `strict_mode_config: { enabled: true, max_resident_memory_percent: N }`.
4. Reconcile (shared mechanism) — converge `strict_mode_config` on existing
   collections via `update_collection`.
5. Verify `@qdrant/js-client-rest@1.18.0` exposes `strict_mode_config` in the
   collection-config types (1.18 SDK should); otherwise pass through the raw
   call path.

**Default:** propose **off** (unset) for the first iteration — turning it on by
default risks rejecting legitimate large-ingest writes on small machines before
we have calibrated a safe threshold. Revisit a default value after live
validation. (Open question, Section 4.)

## 3b. `prevent_unoptimized` / defer point updates — bulk-reindex perf

**What it gives:** during a `force-reindex` bulk load, defers HNSW optimization
until the load finishes (points carry `prevent_unoptimized` until the batch
completes), avoiding repeated incremental index rebuilds → faster full reindex.

**What changes:**

1. `src/core/domains/ingest/` upsert / collection-optimizer path — set the defer
   flag for the bulk phase, clear it at finalize so the optimizer runs once.
2. Exact API surface (`optimizers_config` vs per-update param) to be confirmed
   in the plan — this is a **perf-only**, non-blocking sub-feature and may be
   sequenced last.

## 3c. Deep memory reporting → `get_index_status` extension

**What it gives:** per-component memory breakdown (vectors, sparse, quantized,
payload, HNSW index — RAM vs disk vs page cache) so a leak is visible before it
becomes an OOM. Natural companion to 3a.

**What changes:**

1. `src/core/adapters/qdrant/client.ts` — new
   `QdrantManager.getCollectionMemory(name)` calling the 1.18 memory endpoint
   (likely a raw REST call via `this.call`, since the SDK may not expose a typed
   method).
2. `get_index_status` DTO + handler — add a `memory` section with a **visibility
   split**:
   - **Always (normal user):** collection totals only — `{ ram, disk }` (e.g.
     "Memory: 1.2 GB RAM / 3.4 GB disk"). Two numbers, no noise.
   - **Under `isDebug()` only:** full per-component breakdown (vectors / sparse
     / quantized / payload / HNSW index, each RAM / disk / page-cache).
3. The breakdown is gated by the existing `isDebug()` runtime flag
   (`src/core/infra/runtime.ts`) — same pattern as other debug-only output.

## 3d. Low memory mode — embedded option

**What it gives:** forces on-disk storage to minimize RAM, trading latency for
OOM safety on low-memory machines.

**What changes:**

1. `src/core/adapters/qdrant/embedded/daemon.ts` — pass the low-memory daemon
   config at spawn (Qdrant `config.yaml` / `QDRANT__...` env), driven by env
   `QDRANT_LOW_MEMORY` (default off).

## 3e. `search_max_batchsize` — strict mode (optional, unconfirmed)

**Status caveat:** `search_max_batchsize` appears in Qdrant's blog description
of strict-mode guardrails but is **not** in the verbatim 1.18.0 changelog (which
lists only the reject-on-high-memory strict-mode parameter). First task in the
plan: confirm the field exists in `@qdrant/js-client-rest@1.18.0`
`strict_mode_config`; if absent, **cut this sub-feature**.

**What it gives (if present):** caps batch-search query size. Marginal for
tea-rags (we don't issue large batch searches), but it rides the **same
`strict_mode_config`** as 3a, so it is near-free to expose.

**What changes:**

1. Optional `strict_mode_config.search_max_batchsize` field alongside 3a, env
   `QDRANT_SEARCH_MAX_BATCHSIZE` (unset = no cap). Lowest priority; cut if not
   in 1.18.0.

## Docs (env-var policy)

Per the env-var documentation policy in the bump spec
(`2026-06-29-qdrant-1.18-bump-design.md`, Section F1), every env var this design
introduces is documented in `website/docs/config/environment-variables.md`
(central table) **and** `.env.example`; Qdrant-specific ones also in
`website/docs/config/qdrant.md`:

| Variable                             | Description                                                  | Default     |
| ------------------------------------ | ------------------------------------------------------------ | ----------- |
| `QDRANT_MAX_RESIDENT_MEMORY_PERCENT` | Reject writes when resident RAM exceeds N% of system (1–100) | unset (off) |
| `QDRANT_LOW_MEMORY`                  | Force on-disk storage to minimize RAM                        | `false`     |
| `QDRANT_SEARCH_MAX_BATCHSIZE`        | Cap batch-search size (if kept)                              | unset       |

The release-notes `envChanges[]` mechanism (bump spec F2) surfaces all three as
`new` env entries in the release that ships them.

---

## Reindex / schema-drift

- **No tea-rags reindex** for any sub-feature: `strict_mode_config`, the memory
  endpoint, and the optimizer flags are all server-side config / read-only
  reporting — none touch payload or vector data.
- **No schema-drift trigger** (payload version is unaffected).
- Existing collections get the strict-mode guards via the shared reconcile.

---

## Sequencing within this spec

1. **3a + 3e** (one `strict_mode_config` change + reconcile extension) — highest
   value (OOM guard, beads `b1rs`).
2. **3c** (memory reporting) — pairs with 3a; the user/DEBUG split is decided.
3. **3d** (low-memory daemon mode) — independent, small.
4. **3b** (reindex perf) — perf-only, sequence last; needs API confirmation.

## 4. Open questions for the plan

- **3a default:** off vs a calibrated percentage. Recommend off first, set a
  default after measuring resident-memory headroom during a real reindex.
- **3b API:** confirm `prevent_unoptimized` is an `optimizers_config` setting vs
  a per-update flag in `@qdrant/js-client-rest@1.18.0`.
- **3c endpoint shape:** confirm the exact memory-endpoint path and JSON shape
  against the 1.18 REST API; decide raw-call vs typed-SDK access.
- **3e:** keep or cut, based on whether any tea-rags path issues batch searches.
