Based on the Instead integration patterns visible in the code, a second vendor should inherit these lessons:

- **Rate limits:** Keep vendor-specific throttling in the adapter namespace, so its limits and rate-limit groups don’t leak into shared ports. Map `429` responses into the shared rate-limit error vocabulary, preserving `Retry-After` where available so callers can schedule retries appropriately.

- **Lost webhooks:** Treat webhooks as a prompt to reconcile, not the only source of truth. Reconciliation jobs should query vendor state and apply the same status transitions as webhook handlers. That lets the integration recover when an event is delayed or missed.

- **Failure reasons:** Translate vendor errors into stable, actionable reasons at the adapter boundary. Callers should be able to distinguish cases such as expired authorization, missing scope, quota, rate limits, and transient service failures without parsing vendor response bodies. Preserve vendor-specific reasons only where shared categories cannot express the decision callers need to make.

- **Signed URLs and cassettes:** Keep file bytes off the API client path when the vendor provides signed upload targets. Specs should cover the target negotiation and transfer boundary, but avoid recording usable signed URLs or credentials in VCR cassettes. The visible Instead specs stub API endpoints; check the upload flow specifically for cassette handling before copying its test setup.

- **Entity matching:** Don’t assume a display name is a stable identity. Prefer vendor IDs once linked; make matching rules explicit for initial linking, including normalization, ambiguity, and duplicate entities. Keep any vendor-specific matching behavior inside its adapter or linking service.

One useful constraint from Instead: test the shared contract and caller decisions, while keeping vendor-specific quirks inside the adapter. This avoids making the second provider fit Instead’s API shape when its data model or workflow differs.
