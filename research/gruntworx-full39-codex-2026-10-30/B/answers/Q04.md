Several contracts are called vendor-neutral, but they carry assumptions from **Instead’s API** or **OAuth 2.0**. A second vendor should be checked against these before its adapter is shaped around them.

**OAuth assumptions**

- `HasOauthConnection` and `TokenRefreshable` assume an authorization-code flow with PKCE S256, access and refresh tokens, preemptive refresh, Bearer auth, scopes, and a revocation endpoint. The authorization URL also defaults to `/oauth2/authorize`, `/oauth2/token`, and `/oauth2/revoke`.
- The connection model assumes one grant per firm and stores an Instead-specific PKCE verifier and ceremony state. A vendor using API keys, client credentials, SAML, a different OAuth profile, or multiple connections per firm won’t fit this lifecycle unchanged.
- The shared `InvalidGrantError` assumes that a vendor refusal during refresh means the firm must authorize again. That decision needs checking against the vendor’s actual error semantics.

**Instead API and upload assumptions**

- The export flow assumes the vendor can issue a pre-signed upload target and that TaxDome can transfer file bytes directly to it. The shared transfer path needs revisiting if a vendor requires multipart upload, a client-mediated upload, or bytes sent through its API.
- Capability terms are expressed as formats, max file size, return type, and supported tax years. Those are useful only if the vendor’s constraints can be represented in those terms.
- The mock’s routes and response shapes, and the provider-specific connection/entity/document tables, mirror Instead’s API. They’re examples of one adapter, not a generic provider contract.

**Entity and document model assumptions**

- Instead’s entity model uses its own entity-type vocabulary and maps each return type to an entity type. Linking also assumes a taxpayer can be matched by name and return type when there is exactly one unlinked candidate. A vendor with different taxpayer identity, household, or business semantics needs its own matching rules.
- The shared document state machine has a fixed set of processing states and failure reasons. A new vendor’s statuses need translation into these states; if that loses distinctions callers need, the shared vocabulary should be extended deliberately.
- The shared send record snapshots the provider and return type, and assumes documents are sent under a tax preparation “envelope.” Confirm that the second vendor’s submission unit and lifecycle map cleanly to that model.

The practical boundary is: reuse shared contracts where they describe TaxDome’s decisions, but keep vendor identity, matching, auth ceremony, upload protocol, and status translation in the adapter when those details differ.
