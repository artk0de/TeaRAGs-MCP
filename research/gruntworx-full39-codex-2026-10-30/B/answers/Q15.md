The endpoint handles an Instead delivery in this order:

1. **Verify the signature.** It checks `X-Instead-Signature`, the declared `hmac-sha256` algorithm, and a timestamp within **5 minutes** of now. The HMAC-SHA256 is computed over `timestamp.raw_body`. It accepts either the current or previous configured signing secret. A failed check returns **401**.

2. **Validate the body.** It permits only the expected delivery fields, requires a recognized event type and an event ID, and checks entity and resource IDs are UUID-shaped. Invalid signed deliveries are logged and acknowledged with **200 OK**.

3. **Match and enqueue asynchronously.** Document events are matched to a TaxDome firm through the vendor document and entity IDs. Entity events are matched through the vendor firm ID. If there is no match, no owner, or the async operation cannot be started, the endpoint still acknowledges with **200 OK**. That avoids vendor retries for deliveries TaxDome cannot apply.

**It does not keep a processed-event-ID ledger or explicitly deduplicate deliveries by event ID.** Instead, processing is designed to tolerate repeats: entity events use the UUIDv7 event timestamp and ignore updates older than the entity’s last sync; document events apply the reported current status to the matched send record. So duplicate delivery effects are suppressed through state handling, not through a stored event-ID check.
