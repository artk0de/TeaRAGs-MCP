**Strategy: codegraph row 4 — “How is the tax-automation provider architecture organized today?”**

Сейчас tax automations устроен как общий слой, который обслуживает API и хранит общие состояния, и провайдерские адаптеры, которым делегируются операции с вендором. В registry зарегистрирован только `instead`; наличие `gruntworx` в enum провайдеров само по себе не означает, что для него уже есть адаптер.

### Порты и подключение адаптера

Общий слой находится в `app/services/tax_preparation/tax_automations/`. Его основные порты сгруппированы по операциям:

- **Авторизация:** `Authorizations::Create`.
- **Соединения:** создание и завершение подключения, поиск, обновление и отзыв гранта, проверка его состояния.
- **Отправка:** `Export::ValidateDocuments` проверяет выбранные файлы, а `ExportAsync` ведёт общий сценарий отправки.
- **Документы:** обновление статуса, обработка загрузки и возобновление отправок.
- **Tax preparations:** поиск/создание, слияние и удаление записей.
- **Lifecycle фирмы:** очистка связанных данных при деактивации или удалении.

Это общий API-поверхностный слой: контроллер помечен как универсальный, а для отправки общий `ExportAsync` вызывает `adapter::ExportAsync.call(...)`. См. [контроллер](</Users/Shared/nav-ab/repo-master/app/controllers/tax_preparation/api/v1/firm/tax_automations_controller.rb:3>) и [ExportAsync](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export_async.rb:3>).

Регистрация — `Registry::ADAPTERS`, сейчас `{ instead: TaxPreparation::TaxAutomations::Instead }`. Ключ провайдера выбирает namespace адаптера; общий код через него находит `Connection`, `Client` и сервисы для конкретной операции. Контракт registry требует, чтобы namespace предоставлял модель `Connection`, `Client` с `TokenRefreshable` и вызываемые портами сервисы. Модель Instead `Connection` подключает общие OAuth-поведение и capability contract. См. [Registry](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/registry.rb:3>) и [Instead::Connection](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/instead/connection.rb:1>).

В коде провайдерские реализации расположены под `.../instead/`: авторизация, соединения, документы, webhooks, синхронизация клиентов и отправка. То есть общий порт определяет сценарий, а адаптер выполняет специфичные для вендора шаги и преобразует их результаты в общий формат.

### Capability passport

Passport описывает **возможности провайдера**, поэтому его можно получить без записи подключения конкретной фирмы: registry берёт `Connection.capabilities`. Это `Dry::Struct` с:

- `terms`: условия по каждому типу налоговой декларации — тип декларации, допустимые расширения файлов и максимальный размер в MB;
- `supported_tax_years`: поддерживаемые налоговые годы.

Адаптер реализует `capability_terms` и `supported_tax_years`; общий контракт собирает и проверяет паспорт. Сериализатор преобразует его для API в `return_types` и `tax_years`. Общий export сверяет с возможностями файлы по отдельности, поэтому результат может содержать и принятые, и отклонённые документы. См. [passport contract](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/has_capabilities.rb:22>), [serializer](</Users/Shared/nav-ab/repo-master/app/serializers/tax_preparation/base/tax_automations/connection_serializer.rb:57>) и [валидацию отправки](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export_async.rb:3>).

### Модель данных

- **`FirmSettings`** хранит выбранного провайдера — одна запись на фирму. Enum уже содержит `juno`, `gruntworx` и `instead`, но registry обслуживает только `instead`.
- **`TaxAutomations::Document`** — общая запись отправки документа фирмой через провайдера, привязанная к tax preparation и типу декларации. В ней хранятся snapshot провайдера на момент отправки, статусы обработки/загрузки и причина ошибки. Ограничение уникальности учитывает документ, фирму, tax preparation, provider и return type.
- **`TaxAutomations::TaxPreparation`** — общая оболочка tax preparation, но пока использует таблицу `juno_tax_preparations` и сохраняет Juno-совместимость.
- **Данные конкретного вендора остаются в его моделях.** У Instead это `Connection` для гранта, `Entity` для идентичности налогоплательщика у вендора и `Document` для vendor file handle/path, связанного с общей записью отправки. См. [FirmSettings](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/firm_settings.rb:3>), [общую запись документа](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/document.rb:3>), [TaxPreparation](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/tax_preparation.rb:1>) и [модели Instead](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/instead/entity.rb:3>).

Для GruntWorx это означает, что общий passport и vendor-neutral контракты уже задают часть границ, но его vendor-specific модели и обмен данными могут отличаться. В частности, `gruntworx` уже допустим как provider enum, хотя адаптер пока не зарегистрирован.
