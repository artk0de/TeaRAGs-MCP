**Strategy: EXEMPLAR Reference — “What lessons from the Instead integration should a second vendor inherit?”** Seed tool: `semantic_search` with `proven`, expanded via `find_similar`.

Переносить стоит общие гарантии и шаблоны тестирования. Группы rate limit, словарь ошибок API и правила сопоставления сущностей нужно строить под контракт нового вендора.

1. **Rate limits: разделять throttling, retry и квоты.** Instead ограничивает запросы по API-группам и connection, а приложение дополнительно задаёт общий лимит. Ответы с rate-limit headers обновляют gauge по вендору и группе. Тесты проверяют `Retry-After` на 429; отдельный отказ `USAGE_LIMIT_EXCEEDED` классифицируется как превышение квоты. Для нового адаптера стоит покрыть обе ветки и убедиться, что worker и клиент относят запрос к одной группе. См. [Sidekiq throttling](</Users/Shared/nav-ab/repo-master/config/initializers/sidekiq.rb>), [группы Instead](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/instead/rate_limit_group.rb:3>) и [client specs](</Users/Shared/nav-ab/repo-master/spec/unit/tax_preparation/lib/tax_automations/instead/client_spec.rb:300>).

2. **Потерянные webhooks: событиям нужен backstop через сверку.** Обработчик находит отправку по паре vendor entity/file IDs, допускает повтор события и не откатывает уже более новое состояние. Reconciliation постранично читает папку вендора, применяет статусы известных файлов, затем проверяет по одному те отправки, которых не было в выдаче: файл, которого уже нет, становится `archived`. Неизвестный статус пропускается с записью в лог, чтобы обработать остальную страницу. Для второго вендора стоит описать обе части: доставку событий и способ восстановить состояние, если событие потерялось. См. [webhook processor](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/webhooks/process_document_event.rb:3>), [сверку папки](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/reconcile_statuses.rb:3>) и [сверку отдельного файла](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/reconcile_status.rb:3>).

3. **Failure reasons: переводить vendor-ошибки в общий словарь.** Общий слой хранит свои причины отказа; адаптер мапит известные токены вендора на них. Например, `password_required` становится `encrypted`. Неизвестная причина остаётся без нормализованного reason, но статус ошибки сохраняется; неизвестный статус обработки не должен ломать всю сверку. Тесты должны фиксировать оба случая. См. [маппинг статусов и причин](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/apply_processing_status.rb:8>) и [общую обработку отказов](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/refusals_helper.rb:3>).

4. **Signed URL: тестировать полный цикл, включая объектное хранилище.** Тест Instead проходит `start → upload bytes → finalize → read back` с VCR cassette и бинарным fixture, затем проверяет MIME type и размер. Передача байтов идёт на подписанную цель без OAuth grant; сам клиент проверяет истечение URL и стримит файл. Если GruntWorx тоже выдаёт подписанную цель, сохраните такой end-to-end сценарий и тесты на обязательные поля, тип и размер загружаемых данных. См. [upload implementation](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:243>) и [клиентский spec с cassette](</Users/Shared/nav-ab/repo-master/spec/unit/tax_preparation/lib/tax_automations/instead/client_spec.rb:360>).

5. **Entity matching: автоматизировать только однозначные совпадения.** Instead ищет среди активных, ещё не связанных сущностей той же фирмы и подходящего типа декларации. Имена нормализуются; для физлица есть ограниченный fallback на переставленные имя и фамилию, для бизнеса — нормализация юридических форм. Сущность связывается только при одном кандидате. Несколько совпадений или отсутствие совпадения оставляют её несвязанной; outcome учитывается метрикой. Для GruntWorx сначала стоит использовать его устойчивый внешний идентификатор, если он есть, а собственные правила сравнения имён закрепить отдельными спеками. См. [сервис сопоставления](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/clients/link_entity_by_name.rb:3>) и [его спеки](</Users/Shared/nav-ab/repo-master/spec/services/tax_preparation/tax_automations/instead/clients/link_entity_by_name_spec.rb>).

Эти примеры дают хорошую основу для SDD acceptance criteria: отдельные сценарии на лимиты и квоты, дубли/пропуски/порядок webhook-событий, reconciliation, известные и неизвестные причины, полный upload по signed URL, а также неоднозначное сопоставление сущностей.
