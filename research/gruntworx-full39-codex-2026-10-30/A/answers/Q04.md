Strategy: EXPLAIN — “which parts of the vendor-neutral tax-automation port contracts would not fit a different vendor?”

The **use-case ports** are mostly portable: common code routes authorization, connection management, and export through the registered adapter. The main mismatch is that the adapter boundary currently requires an OAuth-shaped client and connection. Some data contracts also encode assumptions about account identity and document capabilities.

| Contract area | Current assumption | When it won’t fit |
|---|---|---|
| **Authentication** | The registry requires a `Connection` and a `Client` using `TokenRefreshable`. That module implements OAuth authorization-code flow with PKCE S256, client credentials, access/refresh tokens, renewal, and revocation. | A vendor using API keys, client credentials, SSO, or an OAuth flow without PKCE/refresh tokens would need a shim or a broader auth contract. See [Registry](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/registry.rb:3>) and [TokenRefreshable](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/token_refreshable.rb:3>). |
| **Connection record** | `HasOauthConnection` requires encrypted token storage, token expiries, OAuth grant states, and the member who authorized the connection. | A vendor with non-token credentials, a service-owned connection, or different connection lifecycle states would not naturally fit this model. See [HasOauthConnection](</Users/Shared/nav-ab/repo-master/app/models/concerns/tax_preparation/tax_automations/has_oauth_connection.rb:3>). |
| **Provider account binding** | A firm has one selected provider and one `external_tenant_uuid`; reconnecting must land on the same provider account or the connect is refused. | This assumes one stable account identity per firm/provider. It needs reconsideration if GruntWorx has no account ID at authorization time, supports multiple accounts per firm, or allows accounts to be shared differently. See [account binding](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/connections/create.rb:119>). |
| **Capability passport** | Capabilities are vendor-wide and grouped by IRS return type, with accepted file extensions, max file size, and supported tax years. | This is insufficient if capabilities vary by firm/account, or include other constraints such as MIME types, document counts, bundles, or required metadata. See [HasCapabilities](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/has_capabilities.rb:22>). |
| **Document workflow** | Shared code has normalized processing and upload statuses. Instead-specific code maps its `IndexStatus` and file events into those statuses. | The normalized states are reusable only if they represent the second vendor’s lifecycle. Instead’s folder listing, event tokens, entity UUIDs, and archive behavior belong in the adapter. A vendor without folder listing needs a different reconciliation strategy. See [Instead’s status mapper](</Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/apply_processing_status.rb:3>). |
| **Tax preparation model** | The shared model still uses `juno_tax_preparations` and retains Juno associations. | This is legacy-provider coupling, rather than an Instead requirement, but it can constrain a new provider’s data model. See [TaxPreparation](</Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/tax_preparation.rb:1>). |

Instead’s API details are mostly contained correctly: its rate-limit groups, error identifiers, entity-name matching, webhook reconciliation, and signed-upload flow live under `Instead::...`. Those should stay provider-specific. The shared layer should receive normalized outcomes; GruntWorx’s API-specific behavior should not be forced into Instead’s vocabulary.

The clearest contract question for GruntWorx is authentication: **does it support the exact OAuth authorization-code + PKCE + refresh-token lifecycle that `TokenRefreshable` requires?** If yes, much of the connection plumbing can be reused. If not, the auth and connection contract is the part that needs a more general boundary.
