**There are two different things that could be called “the mock.”** The repo has a custom Instead mock transport, but the specs I found use other HTTP stubbing mechanisms.

- **The custom transport** is `Instead::Mock::Adapter` plus `Instead::Mock::Router`. The adapter replaces the socket at the bottom of Faraday’s stack, so requests still pass through the client’s middleware, error mapping, JSON parsing, OAuth flow, and metrics. The router returns synthetic responses for token/revoke, entity, and document endpoints. It derives stable IDs from the firm and request, but stores no state and doesn’t simulate status progression. See [adapter](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/instead/mock/adapter.rb:3>) and [router](</Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/instead/mock/router.rb:3>).

- **There is no switch for that custom transport in the current source.** Its own comment says no client selects it and no flag reaches it. `rg` found `Instead::Mock` only in the adapter and router files, and no `instead_mocks` occurrences in `app/`, `spec/`, or `config/`. So it is defined and internally connected to its router, but not wired into the client or specs.

- **The actual spec switch is dependency injection:** `BaseClient` accepts `transport:`; specs pass a `Faraday::Adapter::Test::Stubs` instance, while calls without one use Faraday’s default adapter. The base-client spec exercises that setup directly in [base_client_spec.rb](</Users/Shared/nav-ab/repo-master/spec/unit/tax_preparation/lib/tax_automations/base_client_spec.rb>). Other Instead service specs use WebMock `stub_request` and Instead response fixtures; for example, the connection-creation spec stubs the token endpoint.

So, **the custom `Instead::Mock::Adapter` wasn’t switched on in the code I could inspect.** The tests mock HTTP through Faraday stubs or WebMock instead. I can’t establish whether that custom adapter was wired in an earlier revision from the current source alone.
