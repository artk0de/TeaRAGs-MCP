**A duplicate blocked by the shared pre-send validation never reaches the vendor.** It appears in `rejected_documents` with one of these reasons:

| Reason | Condition |
|---|---|
| `already_sent` | The document has an `uploaded` send record for the **same return type**, and its processing status is not `archived`. |
| `upload_in_progress` | The document has a send record in `waiting` or `uploading`, **regardless of return type**. |

Both checks are scoped to the **same provider, firm, account, contact and tax year**. See [the duplicate checks](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export/validate_documents.rb:79).

Consequences:

- An uploaded document whose **processing failed** still counts as `already_sent`; upload and processing states are separate.
- An archived send no longer triggers `already_sent`.
- A failed upload does not trigger either duplicate refusal.
- A different provider or year does not collide with that previous send.

Validation runs per document. If some files pass, only those proceed. If all are rejected, the entry point returns successfully with an empty `accepted_documents` list and the rejection details; **it creates no send workflow and makes no vendor call for them**. See [the shared send entry point](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export_async.rb:53).

These checks govern a member’s new send request. Worker retries and reconnect recovery follow separate paths.
