A second vendor should inherit **the reliability contracts and test strategy**, with its own API budgets, status mappings and identity model.

**1. Rate limits belong in the job design**

Instead enforces two budgets: per API group **per connection**, plus an app-wide budget. The group check runs first so a job refused by that limit does not consume the app’s allowance. Unknown groups fall back to a budgeted `default` bucket. See the [throttle configuration](/Users/Shared/nav-ab/repo-master/config/initializers/sidekiq.rb:101).

The transferable lessons are:

- Make each operation job perform at most one vendor exchange, so throttling corresponds to requests.
- Keep interactive uploads and background reconciliation in separate priority lanes.
- Honor `429 Retry-After`, including both seconds and HTTP-date formats.
- Record remaining/reset headers under the same group vocabulary used by throttling.
- Bound transient retries and fail affected uploads when retries run out.

Instead’s limits—such as five document requests/minute/connection—are vendor settings, not defaults for GruntWorx. Also, the [shared retry worker](/Users/Shared/nav-ab/repo-master/app/workers/tax_preparation/tax_automations/operation_worker.rb:9) explicitly warns that throttled rescheduling resets retry counts: an attempt budget is not a wall-clock deadline.

**2. Webhooks need a reconciliation backstop**

Instead periodically reads vendor truth for uploaded documents left in intermediate states. Current defaults select `sent` after one hour and `processing` after twelve hours, within a two-day window. Older records remain unchanged; “give up” does not automatically mean “failed.” These thresholds are [provider-overridable](/Users/Shared/nav-ab/repo-master/app/queries/tax_preparation/tax_automations/documents/reconcile_candidates_query.rb:8).

Its adapter lists files by entity/year, paginates, then individually fetches candidates absent from the listing. An individual document `404` means archived; an inaccessible folder is skipped rather than treating every file as deleted.

Both webhooks and reconciliation use [the same status application service](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/apply_processing_status.rb:3). Duplicate or backward reports do not regress state; unknown statuses do not break an entire page.

A second adapter also needs `Documents::ReconcileStatusesAsync`: the shared sweep calls that contract directly.

**3. Preserve the shared failure vocabulary**

The common reasons are:

`unexpected`, `no_active_connection`, `network_error`, `unauthorized`, `api_error`, `exceeded`, `forbidden`, `encrypted`.

They express recovery behavior, rather than raw vendor errors. The [shared refusal mapping](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/refusals_helper.rb:9) distinguishes:

- quota exhaustion → `exceeded`;
- invalid grant, HTTP unauthorized or insufficient scope → `unauthorized`;
- local policy denial → `forbidden`;
- other terminal vendor refusals → `api_error`.

A vendor HTTP `403` is therefore **not automatically a local permission denial**. Instead additionally maps `password_required` to `encrypted`; unknown processing failures can have no mapped reason.

Only `unauthorized` uploads automatically resume after reconnect. A second vendor must preserve that distinction so reconnect does not retry quota, policy or malformed-request failures.

**4. Signed-URL cassettes need a consistent clock**

A recorded upload target eventually expires relative to today. Instead’s [`:vcr_fixed_time` helper](/Users/Shared/nav-ab/repo-master/spec/support/vcr_fixed_time.rb:3) freezes replay at the cassette’s earliest recording time; new recordings use the real clock, and replay restores the clock afterward.

Inherit this approach instead of extending recorded expirations or bypassing expiry checks. Use live recordings for obtainable vendor responses, HTTP stubs for exceptional/malformed responses, and a mock transport for early development. The retained mock’s synthetic responses cannot establish real vendor behavior.

**5. Entity matching must be conservative**

Instead first reuses a stored taxpayer/entity-type mapping across tax years, avoiding another vendor call. Its creation endpoint is non-idempotent, so retaining the external handle matters.

[Automatic name matching](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/clients/link_entity_by_name.rb:48) considers only active, unlinked entities of the correct type and firm:

- Normalize punctuation, whitespace and case, plus specific business-name variants.
- Link only one unambiguous candidate; never choose the first namesake.
- Try swapped personal names only when direct matching finds none.
- Use an account name for a person only when that account has one contact.
- Emit matching outcomes for observability.

GruntWorx should inherit those safeguards, while defining matching keys and normalization from its own identity model. Its creation idempotency also needs independent verification.
