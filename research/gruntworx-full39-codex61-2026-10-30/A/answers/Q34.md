They use **the `json-schema` gem**, pinned to **6.2.0** in [Gemfile.lock](/Users/Shared/nav-ab/repo-master/Gemfile.lock:652).

The shared [`TaxAutomationsHelpers`](/Users/Shared/nav-ab/repo-master/spec/support/tax_automations_helpers.rb:92) loads the Instead OpenAPI YAML and validates a payload against a named component:

```ruby
def conforms_to_contract?(schema_name, payload)
  JSON::Validator.validate(
    instead_contract.merge(
      '$ref' => "#/components/schemas/#{schema_name}"
    ),
    payload
  )
end
```

Keeping the **whole OpenAPI document** as the schema root lets internal `$ref`s resolve. The contract path is:

```text
specs/TD-95046-instead-integration/contracts/instead_openapi_spec.yml
```

The [client specs](/Users/Shared/nav-ab/repo-master/spec/unit/tax_preparation/lib/tax_automations/instead/client_spec.rb:696) explicitly check:

| Fixture | Component schema |
|---|---|
| `entity.json` | `Entity` |
| `file.json` | `File` |
| `start_upload.json` → `Upload` | `SignedUpload` |
| `token.json` | `TokenResponse` |

They also validate returned entities/files from recorded client calls and reconstruct `SignedUpload` from the client’s mapped upload target to validate that mapping.

**This is explicit payload-schema validation**, not automatic validation of every mock response or the full HTTP exchange. Request URLs, methods, headers and bodies have separate assertions. The disconnected `Mock::Router` does not automatically run this validator on its answers.
