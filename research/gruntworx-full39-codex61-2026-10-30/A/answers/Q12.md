**TaxDome consolidates the local send history under the surviving contact; the merge does not re-upload files or move them through the vendor API.**

The [shared merge service](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/tax_preparations/merge_for_contact.rb:33) handles each source tax preparation:

| Situation | Result |
|---|---|
| Survivor has no preparation for the same **account and year** | Change the source preparation’s `contact_id` to the surviving contact. Existing send records remain attached. |
| Survivor already has that preparation | Move nonduplicate send records onto it, then delete the source preparation. |
| Both preparations contain the same **document + provider + return type** | Keep the survivor’s send record. The duplicate stays on the source preparation and is deleted with it. |

Moved send records retain their existing upload/processing states.

Before deleting the merged preparations, the service calls **the currently selected provider’s** `MergeForContact` hook. Cleanup of discarded records then calls the providers identified by those records.

For [Instead’s adapter](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/merge_for_contact.rb:33):

- If the survivor has no entity of that type, the source entity is reassigned to the surviving contact.
- If it already has one, local vendor-document rows are repointed to that entity.
- The redundant local entity is deleted if TaxDome created it, or unlinked if it originated at Instead.

Those are **local database changes**. Instead’s external file IDs remain unchanged; this code does not perform a remote entity/file merge.
