[`Instead::ExportAsync`](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/export_async.rb:28) receives the tax preparation and **existing shared send records**.

It then:

1. Resolves the firm’s usable connection through `Registry.usable_connection_for(actor.firm)`.
2. Authorizes **`:read` on that connection** using `ConnectionPolicy`.
3. Extracts the send-record IDs and starts:

```ruby
Instead::Documents::ExportAsyncWorkflow.perform_async_operation(
  user,
  actor,
  {
    connection_id: connection.id,
    tax_preparation_id: tax_preparation.id,
    tax_automation_document_ids: [...]
  }
)
```

4. Returns `async_result`, carrying the workflow operation ID.

[The connection policy](/Users/Shared/nav-ab/repo-master/app/policies/tax_preparation/tax_automations/connection_policy.rb:6) first requires the connection to belong to the user’s firm. It allows firm managers and employees with **either `manage_juno_documents` or `manage_tax_software`**, plus explicit editor/sales impersonation cases. Others are denied.

The workflow is enqueued **after the surrounding transaction commits**; rollback starts nothing. The adapter entry point itself makes no vendor call, and the files remain `waiting` until workflow steps run. Shared export authorization and document validation happen upstream.
