The endpoint **verifies the signature first, validates the signed body, then schedules asynchronous processing and returns an empty `200 OK`**. It does **not explicitly deduplicate deliveries by event ID**.

**Signature verification**

It requires:

- `X-Instead-Signature-Algorithm: hmac-sha256`;
- a numeric `X-Instead-Signature-Timestamp` within **±5 minutes**;
- `X-Instead-Signature` matching HMAC-SHA256 of **`"<timestamp>.<raw body>"`**.

Comparison uses `secure_compare`. Both current and previous configured secrets are accepted during rotation. Missing configuration, invalid signatures or stale timestamps produce **`401 Unauthorized`**. See [signature verification](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/instead/webhooks/signature.rb:31).

**Payload validation and routing**

The controller reads **body parameters only**, preventing unsigned query parameters from overriding signed values.

The [event form](/Users/Shared/nav-ab/repo-master/app/forms/tax_preparation/webhooks/tax_automations/instead/event_form.rb:17) requires a supported event type, a nonempty event ID, and UUID-shaped entity/resource identifiers. It permits only selected fields. `IndexErrorReason` is retained only when it resembles a safe lowercase token.

Further validation happens in operation arguments and handlers:

- Document upsert/index events require a recognized `IndexStatus`.
- Entity events require a UUIDv7 event ID; create/update also require name and entity type.
- Document deliveries match an existing **entity UUID + file UUID**.
- Entity deliveries fan out to firms bound to the reported Instead account.

Processing is scheduled as each matched firm’s Owner; document status writes run as System.

**Acknowledgement**

| Outcome | Response |
|---|---|
| Signature rejected | `401` |
| Signed but invalid/unsupported payload | Log and `200` |
| Unknown file/account, missing Owner, or rejected operation arguments | Log and `200` |
| Accepted for asynchronous processing | `200` |

A `200` therefore means **acknowledged**, not necessarily applied. Unexpected unhandled exceptions are not universally converted to `200`. See [the controller](/Users/Shared/nav-ab/repo-master/app/controllers/tax_preparation/webhooks/tax_automations/instead/events_controller.rb:6).

**Duplicates and ordering**

There is no explicit processed-event-ID ledger/check in this webhook flow. Instead:

- Document status application ignores an already-held status and refuses disallowed backward transitions.
- Entity processing extracts occurrence time from the UUIDv7 event ID and skips events older than `synced_at`. Equal-time deliveries can be applied again.

These are state-based replay protections, **not event deduplication or exactly-once delivery**. See [entity processing](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/webhooks/process_entity_event.rb:40).
