Сейчас Tax Automations устроен как **общее ядро с портами и адаптерами провайдеров**. Ядро отвечает за права, выбор провайдера, проверку файлов, записи отправок и жизненный цикл подключения; адаптер — за API вендора и собственные данные.

**Регистрация и контракт адаптера**

В [Registry](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/registry.rb:6) зарегистрирован только `instead`. `gruntworx` уже есть в enum `FirmSettings`, но работающего адаптера за этим значением пока нет. Juno ещё остаётся вне портов.

Провайдер выбирается через `FirmSettings.provider`. Реестр разрешает его в namespace адаптера; для работы со старым подключением клиент определяется по namespace самой connection-модели. Это позволяет корректно обслуживать записи прежнего вендора после переключения.

Namespace адаптера должен предоставлять:

| Контракт | Назначение |
|---|---|
| `Connection` | Поиск подключения через `.for_firm` / `.usable_for`, состояния и паспорт возможностей |
| `Client` с `TokenRefreshable` | Обмен, обновление и отзыв токенов; текущий пример наследуется от `BaseClient` |
| `Authorizations::Create` | Начало подключения, возвращает `authorization_url` |
| `Connections::Create` | Завершение подключения, возвращает connection |
| `ExportAsync` | Принимает общий tax preparation и записи отправок, запускает workflow вендора |
| `DestroyForTaxPreparations` | Очистка данных адаптера для удаляемых деклараций |
| `MergeForContact` | Обработка объединения контактов |
| `DestroyForFirm` | Полная очистка данных фирмы |

Это контракт через константы, методы и `ServiceResult`, а не отдельный формальный interface. `FEATURE_FLAGS` дополнительно определяет доступность провайдера фирме.

**Какие общие порты уже есть**

- Подключение: `Authorizations::Create`, `Connections::{Create, Find, Disconnect, DisconnectAll, Renew, Revoke, VerifyGrant}`.
- Отправка: `ExportAsync`, проверка `Export::ValidateDocuments`, восстановление `Documents::ResumeSends`.
- Передача байтов: `Documents::TransferBytesToPresignedTarget` для подписанной цели загрузки.
- Жизненный цикл данных: удаление деклараций, объединение контактов, очистка фирмы.

[Общий ExportAsync](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export_async.rb:53) проверяет права и подключение, валидирует документы по паспорту, создаёт общие записи и передаёт их в `adapter::ExportAsync`. Порядок API-вызовов и workflow остаются внутри адаптера.

**Паспорт возможностей**

[HasCapabilities](/Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/has_capabilities.rb:17) — типизированный `Dry::Struct`, описывающий **вендора, независимо от наличия connection-записи**:

```ruby
{
  terms: [
    {
      return_type: "1040",
      accepted_file_formats: ["pdf"],
      max_file_size_mb: 20
    }
  ],
  supported_tax_years: [...]
}
```

Форматы и лимит задаются **для каждого типа декларации**. Список поддерживаемых типов выводится из `terms`; отдельного дублирующего списка нет. Адаптер реализует `.capability_terms` и `.supported_tax_years`.

Паспорт проверяет типы значений, повторные объявления форм, положительный размер и диапазон годов. Ошибки обнаруживаются при вызове `.capabilities`, поэтому этот вызов необходимо проверять в контрактных тестах адаптера. API преобразует паспорт в `tax_years` и `return_types` с названиями, семейством personal/business и ограничениями файлов.

**Модель данных**

| Сущность | Ответственность |
|---|---|
| `FirmSettings` | Один выбранный провайдер на фирму; `external_tenant_uuid` привязывает фирму к аккаунту вендора |
| Общий `TaxPreparation` | Конверт по фирме, клиенту, контакту и году; содержит текущие `return_type` и EIN |
| Общий `Document` | Отправка исходного документа конкретному провайдеру под конкретным типом декларации |
| Vendor `Connection` | Учётные данные, автор подключения, сроки и состояния |
| Vendor entities/documents | Внешние идентификаторы, пути и прочая специфика API |

Общий [TaxPreparation](/Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/tax_preparation.rb:3) пока физически живёт в `juno_tax_preparations` и сохраняет переходные связи Juno.

[Запись отправки](/Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/document.rb:7) уникальна по `(firm, tax_preparation, document, provider, return_type)`. Провайдер и тип декларации фиксируются на момент отправки. Здесь находятся две отдельные машины состояний:

- upload: `waiting → uploading → uploaded / failed`;
- processing: `sent`, `processing`, `processed`, `error`, `archived`, `exceeded`.

У Instead отдельные `Connection`, `Entity` и `Document`: entity представляет налогоплательщика у вендора, а vendor document хранит внешний handle, путь и связь с общей отправкой. Для GruntWorx эта структура не обязательна.

**Что переносить в SDD GruntWorx из опыта Instead**

Нужно сохранить проверенные сценарии: переключение провайдера только после успешного подключения, привязку аккаунта, безопасный отзыв старого grant при конкурентном reconnect, повторное использование записей отправки, запуск workflow после commit, восстановление отправок после авторизации и очистку данных прежних провайдеров.

При этом текущие общие контракты уже предполагают OAuth и местами presigned upload. Их применимость к GruntWorx нужно проверить по его документации; одинаковая архитектура адаптеров не гарантирует одинаковый протокол.

Зафиксированы ваши ограничения: **первый этап на моках**, **TD-102837 входит в спеки**, опыт Instead учитывается без копирования его модели. Содержимое Jira и документы GruntWorx здесь недоступны, поэтому конкретные изменения портов пока не определены. SDD-файлы не созданы: workspace доступен только для чтения.
