**The boundary is vendor-neutral in dispatch, but still assumes an OAuth-connected, document-oriented vendor.** Some assumptions are mandatory contracts; others are optional helpers shaped by Instead.

| Area | Assumption embedded today | Where another vendor would struggle |
|---|---|---|
| **Credentials and connection state** | `Connection` supplies encrypted access/refresh tokens, expiry fields and `HasOauthConnection` states. “Usable” means the grant can be refreshed. | API keys, Basic Auth, certificates, service accounts, or OAuth grants without refresh tokens do not naturally satisfy this contract. |
| **Connecting** | Authorization starts by returning `authorization_url`; completion accepts `code` and `redirect_uri`. | Credential-entry forms, client-credentials OAuth, device authorization or asynchronous provisioning need a different connection flow. |
| **Request authentication** | Every `BaseClient#request` obtains an access token; an HTTP `401` triggers forced refresh. | A `401` caused by an invalid API key or vendor-specific authorization rule cannot be repaired that way. |
| **Disconnecting and recovery** | Disconnect retains tokens until asynchronous revocation; renewal and grant verification are shared operations. | Vendors with no token-revocation endpoint, manual credential rotation or different credential lifecycles need different semantics. |
| **Account binding** | One selected provider and one external tenant binding per firm. | Multiple vendor accounts, offices or credentials selected per client are outside that selection model. |
| **Uploads** | The shared signed-target implementation models a multipart form POST. | Raw signed PUT, required signed headers, direct API uploads and resumable uploads do not fit that helper. |
| **Capabilities** | A class-level passport describes static file extensions and an integer MB limit per return type, plus a vendor-wide year list. | Account-specific entitlements, different years per form, page limits, product options or batch limits cannot be represented directly. |
| **Submission and results** | The common record represents one source document sent under a provider, tax preparation and return type. | Job/package-oriented vendors need adapter records that translate job-level acceptance and results onto individual document records. |
| **Reconciliation** | A registered adapter must accept stale document IDs through `Documents::ReconcileStatusesAsync`; the sweep requires a `connected` row. | A vendor without status reads cannot implement equivalent recovery; non-OAuth connection models still face the state assumption. |

The strongest leaks are these:

**OAuth is part of the shared substrate, not merely the Instead adapter.**  
[`BaseClient#request`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:280) always enters `with_access_token` and refreshes on unauthorized responses. [`HasOauthConnection`](/Users/Shared/nav-ab/repo-master/app/models/concerns/tax_preparation/tax_automations/has_oauth_connection.rb:28) requires token/status columns and guards connection transitions using both access and refresh tokens. Renaming these types would not make the contract authentication-neutral.

The common [connection completion service](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/connections/create.rb:17) also exposes OAuth callback parameters. API-key onboarding would require a different core entry point or fabricated OAuth-shaped behavior.

**The signed-upload abstraction is narrower than its name suggests.**  
`PresignedUploadTarget` carries `http_method`, but [`upload_to_signed_target`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:243) always calls `.post` with multipart fields. Its constructor requires a nonempty `fields` hash, so a valid signed PUT URL with no form fields is rejected.

This is an optional helper: an adapter’s `ExportAsync` can own a different upload workflow. It becomes a portability problem only if treated as the universal upload port.

**Some shared export rules encode Instead’s storage behavior.**  
[`ValidateDocuments`](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export/validate_documents.rb:79) rejects an already-uploaded, nonarchived document and permits another send after archive. Its rationale explicitly depends on Instead’s per-entity path collisions and archive behavior. A vendor supporting revisions, overwrite, or repeated jobs may need different duplicate-send rules.

**The failure vocabulary is useful, but its recovery policy is OAuth-shaped.**  
The shared [`RefusalsHelper`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/refusals_helper.rb:25) maps insufficient scope and invalid grant to `unauthorized`; reconnect resumes those uploads. A second vendor must distinguish recoverable credentials from missing permissions or entitlements that reconnect cannot fix. Blanket terminal treatment of statuses such as `404` and `423` also needs checking against that vendor’s operation semantics.

**Several Instead-specific choices are already correctly isolated.**  
Entity types and name matching, per-connection rate-limit groups, entity/year folder pagination, `IndexStatus` mapping and the three-step upload workflow live inside Instead. A second adapter should not inherit them. PKCE storage is also on Instead’s connection model.

The shared state machines, ownership checks, provider snapshots and common failure reasons remain useful domain contracts. The main compatibility questions are authentication, submission identity, duplicate-send semantics and capability granularity. These are source-backed limitations; whether GruntWorx actually conflicts with each one still requires its API contract. The dependency report judged no edges for this scope, so it provides no additional verdict on protocol fit.
