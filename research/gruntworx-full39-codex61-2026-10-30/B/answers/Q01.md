Сейчас архитектура разделена на общий слой `TaxPreparation::TaxAutomations` и адаптеры провайдеров. **Через общий слой работает только Instead.** Juno ещё использует прежнюю реализацию; GruntWorx есть в enum, но адаптер не зарегистрирован.

Ниже — состояние по доступному коду и выводы для будущей спеки GruntWorx.

**Общие порты**

Это сервисы и соглашения об именах внутри namespace, без отдельного формального интерфейса адаптера.

| Область | Общий слой |
|---|---|
| Подключение | `Authorizations::Create`, `Connections::Create` — запуск авторизации и завершение подключения |
| Состояние подключения | `Connections::Find`, `Disconnect`, `DisconnectAll` |
| Жизненный цикл credentials | `Renew`, `VerifyGrant`, `Revoke` и фоновые workers |
| Отправка | `ExportAsync`, `Export::ValidateDocuments` |
| Подготовка декларации | `TaxPreparations::FindOrCreate`, `TaxPreparationPrefills::Find` |
| Статусы документов | `Documents::UpdateStatus`, `FailUpload`, `BroadcastStatus` |
| Восстановление | `ResumeSends`, периодический `ReconcileSweepWorker` |
| Очистка и CRM-события | Удаление фирмы, клиента, контакта; перенос документов; объединение контактов |

Например, общий [`ExportAsync`](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export_async.rb:53) проверяет права и capability passport, отдельно принимает или отклоняет каждый файл, создаёт общие записи отправки и передаёт их в `adapter::ExportAsync`. Последовательность вызовов vendor API принадлежит адаптеру.

**Как подключается адаптер**

[`Registry`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/registry.rb:6) содержит статические `ADAPTERS` и `FEATURE_FLAGS`. Сейчас там только `instead`.

Основные способы разрешения:

- `adapter_for(firm)` — через выбранный `FirmSettings.provider`;
- `adapter_for_provider(provider)` — по явному имени, в частности при переключении провайдера;
- `client_for(connection)` — по namespace самой connection;
- `adapters` / `connections_for(firm_id)` — обход провайдеров для фоновой работы и очистки.

Namespace адаптера должен предоставлять то, что вызывают общие порты:

```text
Connection
Client
Authorizations::Create
Connections::Create
ExportAsync
Documents::ReconcileStatusesAsync
DestroyForFirm
DestroyForTaxPreparations
MergeForContact
```

`Connection` предоставляет lookup по фирме, состояния подключения и `.capabilities`. Текущий `Client` строится на `BaseClient`, который включает `TokenRefreshable`: OAuth exchange, refresh и revoke, общий HTTP error mapping, метрики и rate-limit handling. Для такого клиента обязательны vendor hooks `base_url`, `auth_headers`, `vendor_error_message` и объявление `oauth2_settings`.

**Capability passport**

[`HasCapabilities`](/Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/has_capabilities.rb:18) описывает возможности провайдера **на уровне класса Connection**, поэтому паспорт можно получить без сохранённого подключения.

Его структура:

```ruby
{
  terms: [
    {
      return_type: "1040",
      accepted_file_formats: ["pdf"],
      max_file_size_mb: 20
    }
  ],
  supported_tax_years: [...]
}
```

Это пример структуры, не параметры GruntWorx.

Форматы и размер задаются отдельно для каждого return type. Список поддерживаемых форм выводится из `terms`; годы адаптер вычисляет при обращении. `Dry::Struct` проверяет типы, расширения, положительный размер и границы годов; повторное объявление одной формы тоже отклоняется.

Паспорт используется для проверки экспорта и сериализуется для UI как `tax_years` и `return_types` с названием формы, семейством personal/business и файловыми ограничениями. У Instead сейчас поддерживаются текущий год и два предыдущих.

**Модель данных**

| Модель | Назначение |
|---|---|
| `FirmSettings` | Одна запись на фирму: выбранный провайдер и привязка к внешнему tenant |
| `TaxPreparation` | Общий конверт декларации: фирма, клиент, контакт, год, return type, EIN, business name |
| `TaxAutomations::Document` | Один документ, отправленный провайдеру под конкретным конвертом и return type |
| `Instead::Connection` | Одна connection на фирму, авторизовавший сотрудник, encrypted tokens, сроки, состояние, PKCE |
| `Instead::Entity` | Внешний налогоплательщик: UUID, entity type, локальная привязка, источник и состояние синхронизации |
| `Instead::Document` | Vendor-данные отправки: внешний UUID, путь и ссылка на Instead entity |

Общий `TaxPreparation` пока физически хранится в `juno_tax_preparations`: в модели остаются Juno associations и ransackers. Общий код адресует конверт через собственные `client_id` / `contact_id`.

В [`TaxAutomations::Document`](/Users/Shared/nav-ab/repo-master/app/models/tax_preparation/tax_automations/document.rb:3):

- ключ уникальности — `(firm, tax_preparation, document, provider, return_type)`;
- `provider` и `return_type` сохраняются на момент отправки;
- загрузка имеет состояния `waiting → uploading → uploaded/failed`;
- обработка имеет отдельные состояния `sent`, `processing`, `processed`, `error`, `archived`, `exceeded`;
- общий `failure_reason` описывает причину ошибки.

Таким образом, смена провайдера или формы декларации не меняет принадлежность прежних отправок.

**Что перенести из опыта Instead в спеки GruntWorx**

1. Сохранить разделение общей отправки и vendor-моделей. Модель GruntWorx должна следовать его API; необходимость аналога Instead Entity пока не установлена.
2. Зафиксировать частичное принятие файлов, защиту от повторной и параллельной отправки, retry/resume и запуск фоновой работы после commit.
3. Определить отображение vendor statuses в общие состояния, обработку повторных и устаревших событий, восстановление после пропущенных уведомлений.
4. Сохранить безопасное переключение провайдера: прежнее подключение освобождается после успешного нового; старые отправки сохраняют provider.
5. Проверить ограничения общих портов: сейчас они предполагают OAuth, refresh-token expiry, connection state machine и определённую семантику повторной отправки. Соответствие GruntWorx этим предположениям ещё требует документации.

Для моков есть важная деталь: текущие [`Instead::Mock::Adapter`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/instead/mock/adapter.rb:3) и `Router` **не подключены к клиенту и feature flag**. `BaseClient` использует injected test transport либо стандартный Faraday adapter. Поэтому рабочий `instead_mocks` в текущем коде не подтверждён.

Для GruntWorx стоит зафиксировать явное подключение mock transport на HTTP-уровне, чтобы сохранить реальные сериализацию, error mapping и метрики. Сценарии и модель моков нужно строить по контракту GruntWorx.
