The shared client separates **HTTP error classification**, **request metrics**, and **send failure handling**.

**HTTP status → error**

| Status | Error |
|---|---|
| 400 | `BadRequestError` |
| 401 | `UnauthorizedError` |
| 403 | `ForbiddenError` |
| 404 | `NotFoundError` |
| 422 | `UnprocessableEntityError` |
| 423 | `LockedError` |
| 429 | `RateLimitedError` |
| 500 | `ServerError` |
| 503 | `ServiceUnavailableError` |
| Other ≥500 | `ServerError` |
| Other ≥400 | `RequestError` |

Statuses below 400 pass through. The adapter’s `vendor_error_class(body)` can override classification; `vendor_error_message(body)` supplies the message, with a localized fallback. Errors retain the response body, HTTP code and headers.

401 responses trigger forced token renewal and bounded retries. Network failures become `NetworkError`; exhausted connection-lock retries become `ConnectionBusyError`. `RateLimitedError#retry_after` understands seconds and HTTP dates.

See [`BaseClient`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:154).

**Metrics emitted by the client and token layer**

| Metric under `tax_automations` | Labels | Meaning |
|---|---|---|
| `requests_duration` | `vendor`, `operation` | Duration histogram, in seconds |
| `failed_requests_total` | `vendor`, `operation`, `reason` | Failed requests |
| `rate_limit_remaining` | `vendor`, `group` | Remaining budget from `X-RateLimit-Remaining` |
| `rate_limit_reset_seconds` | `vendor`, `group` | Seconds until the epoch in `X-RateLimit-Reset`, clamped at zero |

Operations include `api_request`, `connect`, `reconnect`, `token_refresh`, `token_revoke`, and `upload_transfer`.

Failure metric reasons include `HTTP_ERROR: <status>`, `NETWORK_ERROR: <exception class>`, `LOCK_TIMEOUT`, and `INVALID_GRANT`. Each rejected 401 attempt is counted. A failed refresh can count under both `token_refresh` and the API request that needed it, so totals should be interpreted by operation.

See [metric definitions](/Users/Shared/nav-ab/repo-master/config/initializers/yabeda.rb:33).

**Refusal → persisted failure reason**

Send services use [`RefusalsHelper`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/refusals_helper.rb:7):

| Error | Failure reason |
|---|---|
| `QuotaExceededError` | `exceeded` |
| `InsufficientScopeError` | `unauthorized` |
| `InvalidGrantError` | `unauthorized` |
| `UnauthorizedError` | `unauthorized` |
| Application policy denial | `forbidden` |
| Other terminal refusals | `api_error` |

Other terminal refusals include HTTP forbidden/not-found/locked/bad-request/unprocessable responses and incomplete or expired upload targets. **An ordinary vendor HTTP 403 maps to `api_error`; application policy denial maps to `forbidden`.**

`refuse!` marks affected uploads failed, scoped to the connection’s firm. It reports scope, bad-request, unprocessable and incomplete-target errors to `ErrorReporter`. Policy denials and invalid grants are then re-raised for worker-level handling.

429, server errors and network errors are outside that terminal-refusal list and continue through retry handling. The HTTP client itself does not persist document failure reasons.
