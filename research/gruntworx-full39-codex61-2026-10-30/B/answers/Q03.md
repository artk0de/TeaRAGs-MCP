A second vendor should inherit the operational safeguards, while defining its own limits, status mappings and identity model.

1. **Rate limits must shape the workflow.** Instead uses separate budgets per API group and connection, plus an app-wide budget. The narrower threshold is checked first so rejected work does not consume the app budget. Workers perform bounded vendor operations and honor `429 Retry-After`, including HTTP-date values. Production limits differ from development (`docs`: 60 versus 5 requests/minute), so keep limits configurable. Distinguish temporary throttling from quota exhaustion: waiting helps only the former. See [throttle configuration](/Users/Shared/nav-ab/repo-master/config/initializers/sidekiq.rb:101) and [shared retry rules](/Users/Shared/nav-ab/repo-master/app/workers/tax_preparation/tax_automations/operation_worker.rb:37).

2. **Lost webhooks need a bounded recovery path.** The shared sweep runs every 30 minutes. Defaults select uploaded sends still `sent` after one hour or `processing` after twelve hours, with a two-day lookback; providers can override these windows. Instead reconciles paginated folder listings, then individually reads files missing from those listings. A missing folder does not establish that every file was deleted; an individual file’s 404 maps to archive under Instead’s semantics. Webhooks and reconciliation share one status mapper, making duplicate reports harmless and refusing backward transitions. Missing or unknown vendor statuses leave records unchanged. The second vendor must define equivalent recovery semantics explicitly. See [candidate selection](/Users/Shared/nav-ab/repo-master/app/queries/tax_preparation/tax_automations/documents/reconcile_candidates_query.rb:9) and [shared status mapping](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/documents/apply_processing_status.rb:3).

3. **Keep failure reasons stable and actionable.** The shared vocabulary is `unexpected`, `no_active_connection`, `network_error`, `unauthorized`, `api_error`, `exceeded`, `forbidden`, `encrypted`. Vendor identifiers stay inside the adapter. For example, Instead maps `password_required` to `encrypted`; an unrecognized processing failure becomes `error` without inventing a reason. Separate terminal refusals from transient failures, and distinguish authorization, quota and application-contract problems. Preserve separate upload and processing states: successful transfer does not mean successful processing. See [refusal classification](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/refusals_helper.rb:7).

4. **Signed-upload cassettes need clock control and credential scrubbing.** Recorded targets expire. `:vcr_fixed_time` freezes replay at the cassette’s first `recorded_at`, preserving realistic expiry checks instead of disabling them. Recording hooks scrub policies, signing credentials/signatures and client secrets from response and request bodies, including multipart requests. Bearer/token scrubbing currently recognizes Instead’s host specifically, so another vendor needs that coverage extended. Record supported live exchanges, stub exceptional responses, and test expired or incomplete targets separately. See [clock handling](/Users/Shared/nav-ab/repo-master/spec/support/vcr_fixed_time.rb:3) and [recording filters](/Users/Shared/nav-ab/repo-master/spec/spec_helper.rb:164).

5. **Entity matching must prefer certainty over convenience.** Instead first reuses an existing local binding, then searches active, unlinked entities within the same firm and entity type, and creates only afterward. Matching normalizes punctuation, whitespace and case; business matching also normalizes legal-form spellings and `&`/`and`. Personal matching permits swapped first/last names as a fallback and account-name matching only for a sole contact. **Ambiguous matches never auto-link.** Matching outcomes are measured. Persist external identity because Instead’s create operation is not idempotent, and explicitly address retries after “vendor created it, local persistence failed.” A second vendor should adopt these safeguards only where its identity contract supports them. See [matching rules](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/instead/clients/link_entity_by_name.rb:3).

For GruntWorx’s mock phase, these become acceptance scenarios: throttling, missing notifications, duplicate/out-of-order reports, terminal versus retryable failures, expiring upload targets, and ambiguous taxpayer matches. Its actual API contract must determine the expected outcomes.
