**The adapter dispatch is vendor-neutral; several contracts underneath it assume an Instead-style OAuth connection and document workflow.** These are the main mismatches a different vendor could expose.

| Shared contract | Assumption embedded today | Where it stops fitting |
|---|---|---|
| Connection authorization | `Authorizations::Create` returns an `authorization_url`; the shared callback accepts OAuth `code`, `state`, errors and `redirect_uri` | API-key entry, service credentials, device authorization or provisioning without a browser callback |
| Connection lifecycle | `HasOauthConnection` requires access/refresh tokens, expiries and grant states. `usable?` means the connection can refresh | Credentials without refresh tokens; connections needing verification, provisioning or suspension states |
| Base HTTP client | `BaseClient` unconditionally includes `TokenRefreshable`; authenticated requests acquire an access token, and 401 triggers refresh | API keys, request signing, mTLS, or a 401 that should not initiate renewal |
| Background connection maintenance | Keep-alive queries `refresh_expires_at`; revocation requires a stored refresh token and calls `revoke_tokens!` | Non-expiring credentials, no remote revocation endpoint, or a different credential lifecycle |
| Provider/account selection | One selected provider per firm, one tenant binding on `FirmSettings`; switching releases the previous connection | Multiple simultaneous providers, multiple external accounts, or credentials scoped per user |
| Export identity | One send record per document, envelope, provider and return type | Batch/job identity, multiple processing products, versioned submissions or repeated independent runs |
| Duplicate handling | An uploaded, non-archived document is rejected as `already_sent`; archiving permits another send | Vendors allowing repeated submissions, or whose archive state does not free a submission identity |
| Signed upload utility | Target requires nonempty form fields; transfer always performs multipart **POST**, despite carrying `http_method` | Presigned PUT, header-authenticated uploads, direct API uploads or chunked transfer |
| Status recovery | Reconciliation selects uploaded documents in `sent`/`processing`, using `uploaded_at` and fixed recovery windows | Job-level progress, long-running processing, synchronous completion or recovery based on last progress |
| Reconnect recovery | Reconnection automatically retries uploads failed as `unauthorized` through `ExportAsync` | Work needing job resume/status lookup rather than re-export, especially where resubmission can duplicate work |
| Capability passport | Static vendor-wide terms: form → extensions and per-file size; one shared list of supported years | Account-specific capabilities, year-specific form support, batch/page limits, processing modes or destination software constraints |

Some particularly concrete examples:

- [`BaseClient`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:11) combines HTTP transport, OAuth and a particular signed-upload mechanism. Those are independently reusable concerns, but currently arrive together.
- [`ValidateDocuments`](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/export/validate_documents.rb:96) contains a provider-wide duplicate rule justified by Instead’s entity/path behavior. That rule runs before the second adapter receives the export.
- [`ResumeSends`](/Users/Shared/nav-ab/repo-master/app/services/tax_preparation/tax_automations/documents/resume_sends.rb:50) retries against the mutable tax-preparation record. Sends snapshot `return_type`, but resumption groups them by envelope and passes its current values. A second adapter must not silently interpret old sends using a subsequently changed form.
- [`PresignedUploadTarget`](/Users/Shared/nav-ab/repo-master/app/lib/tax_preparation/tax_automations/base_client.rb:50) looks general because it carries `http_method`, while its validation and transfer implementation specifically describe a signed form POST.

The failure vocabulary is reasonably reusable, but its **policy is less neutral**. `unauthorized` participates in automatic reconnect recovery; `InvalidGrantError` receives special worker handling; target expiry is treated as a terminal upload refusal. A vendor may need credential replacement, target renewal or submission lookup instead. Those decisions should be adapter behavior rather than consequences of a shared error label.

There is also older Juno coupling: the common envelope still uses `juno_tax_preparations`, and authorization accepts legacy `manage_juno_documents` rights. That is migration debt alongside the Instead/OAuth assumptions.

For a second vendor, I would retain registry dispatch, authorization boundaries, shared document reporting and broadcasts. I would separate **connection setup/credential lifecycle**, **submission identity and retry policy**, and **transfer/reconciliation strategy** into explicit adapter contracts. Instead’s entity matching and three-step upload already belong inside its adapter; another vendor need not reproduce them.

These are code-level incompatibility candidates. Without the GruntWorx contract and TD-102837 contents, they are not yet confirmed GruntWorx requirements.
